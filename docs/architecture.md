# Architecture

## Ownership

`with-site-tools` owns reusable behavior that remains meaningful when a customer
switches themes. Visual foundations, block-style variations, templates,
patterns, and project-specific assets remain in the theme.

The plugin never loads files from `with-base` and the theme never needs this
plugin to boot.

## Feature paths

Every file owned by a feature lives together below `src/`:

```text
src/blocks/<namespace>/<block>/<feature>/
src/media/<feature>/
src/site/<feature>/
src/plugins/<plugin-directory>/<feature>/
```

The feature directory contains one `index.php` with its registration,
activation check, callbacks, and WordPress hooks. It can also contain
`editor.js`, `style.scss`, and feature assets as needed. There are no parallel
feature directories in the plugin root. Compiled JavaScript and CSS mirror the
source path below `build/`; PHP runs directly from `src/`.

Each `index.php` calls:

```php
$feature_slug = with_site_tools_register_feature(
	__DIR__,
	__( 'Feature label', 'with-site-tools' ),
	__( 'Feature description.', 'with-site-tools' )
);

if ( ! with_site_tools_is_feature_enabled( $feature_slug ) ) {
	return;
}

// Feature callbacks and WordPress hooks.
```

There is no `feature.json` and no central hand-maintained feature list. The path
defines the slug, settings group, asset path, and optional plugin dependency.
The plugin bootstrap discovers `index.php` entrypoints directly with PHP from
the supported semantic paths. Adding a correctly placed feature therefore needs
no generated loader, second PHP entrypoint, registry edit, or npm command.

## Defaults

The option `with_site_tools_feature_settings` stores only explicitly enabled
feature slugs. Missing keys are always disabled. Adding a feature in a plugin
update cannot silently change an existing site.

## Assets

Editor scripts load only for enabled and available features. They are enqueued
through `enqueue_block_editor_assets` before the Editor initializes, so block
registration filters and controls are available from the first render. Block
CSS is registered with `wp_enqueue_block_style()` so WordPress can load it with
its owning block. JavaScript dependency metadata comes from the `.asset.php`
files generated by `@wordpress/scripts`. Standalone CSS uses the compiled file
modification time as its development cache version.

Optional plugin integrations derive their dependency from the directory
immediately below `plugins/`. They load only when a site-active or
network-active plugin uses that directory.

## Compatibility

The plugin reads existing serialized `withBase...` block attributes for
backward compatibility. New edits are stored with `withSiteTools...`
attributes. Legacy CSS hooks are emitted only while rendering legacy content.
