# Architecture and ownership

## Why the plugin is separate from the theme

With Site Tools owns reusable behavior that remains meaningful when a customer
switches themes. Visual foundations, block style variations, templates,
patterns, and project-specific assets remain theme responsibilities.

This boundary lets a theme boot without the plugin and lets the plugin operate
without loading theme files. It also prevents reusable site behavior from being
lost during a theme change.

## Why features are opt-in

The plugin stores only explicitly enabled feature slugs. A newly shipped
feature therefore cannot silently alter an existing site. Optional integrations
also check their plugin dependency before they can be enabled.

## Why paths define feature identity

Each feature owns one semantic directory below `src/`. Its path determines the
slug, settings group, asset path, and optional plugin dependency. PHP discovers
supported `index.php` files directly, so the filesystem and runtime registry
cannot drift apart through a second hand-maintained list.

Compiled JavaScript and CSS mirror the source paths below `build/`; PHP and
static feature assets run directly from `src/`. Keeping all parts of a feature
together makes ownership and removal visible.

## How assets are loaded

Editor scripts load only for enabled, available features and before the editor
initializes. Block CSS is registered with `wp_enqueue_block_style()` so
WordPress can load it with its owning block. Dependency and version metadata
come from files generated by `@wordpress/scripts`.

## How legacy content remains valid

Features migrated from `with-base` continue to read existing serialized
`withBase*` block attributes. New edits use `withSiteTools*` attributes, and
legacy CSS hooks are emitted only while rendering legacy content. This keeps
stored content functional without making the theme a runtime dependency.
